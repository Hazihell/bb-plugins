## Security / correctness

D-001 is not fully satisfied. Confirmation accepts only an opaque random one-use token and never raw ids; replay/expiry behavior is correct. Server family reads recursively include hidden and archived descendants, fail closed on incomplete enumeration and unknown live statuses, reject non-root ids through parentThreadId, cap work, and normalize failure messages. Arbitrary valid root ids can be supplied only at preview and are then bound into the token, consistent with the accepted RPC contract. The material authorization defect is that the capability binds roots but not the reviewed descendant topology or count: newly attached quiet descendants expand the irreversible cascade after user review. Confirmation must compare the re-read descendant identity set or at least the expected authoritative scope against the preview and skip/re-preview on drift. The current-thread guard is also bound from the client-supplied protectedThreadId rather than independently derived, so it should remain documented as a UI-intent guard rather than server authentication.

## Design / maintainability

D-002 and D-003 are implemented cleanly with focused pure helpers, stable family-level filtering, and the native project-aware composer. The coordinator/adapter split is testable and sequential outcome handling is understandable. PendingPreview should carry the previewed descendant scope as the design states, with a topology-drift regression test. Result presentation should retain and render per-id skipped/failed outcomes (or force selected families visible independently of the active preset/search) so partial recovery does not depend on aggregate text. A regression test should cover a quiet child added between preview and confirm and a selected quiet family becoming protected while selection mode is active.
